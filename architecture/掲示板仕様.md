# ■ ディレクトリ  

Square 掲示板機能モジュール  

# ■ 目的  

ギルドメンバーがコミュニケーションを行うための掲示板機能を提供する。  

主な用途  

- 雑談  
- 技術質問  
- ナレッジ共有  
- 人材・案件募集  
- 運営告知  

# ■ 機能概要  

- markdown記法をベースにしたリッチUI  
- XSS対策  
- 不適切発言チェック（NGワード）  
- 不適切発言モデレーション  
- 表示制御（不適切レベルで切り分け：UI優先）  
- いいね機能  
- 通報機能  
- userprofileリンク機能  
- タグ付け機能  

# ■ 関連テーブル一覧  

- users // ユーザーテーブル  
- square // 文書データ（内部にリスクスコア、および親文書キー `parent_id` を保持）  
- square_likes // いいねデータ（user_id × square_id）  
- square_reports // 通報データ  
- tags // タグテーブル  
- square_tags // 掲示板_タグ中間テーブル  
- square_logs // ログテーブル（通報・モデレーション等の履歴）  

# ■ モジュール概要  

- 掲示板投稿およびコメント投稿（小文書）はサーバーコンポーネントを中心に処理を行う。  
- 元投稿削除時は、内容（content等）を「内容が削除されています」に置き換える。画面上は元投稿者などの情報は非表示（または匿名扱い）とするが、削除された内容に対してぶら下がっているコメント（小文書）のツリー構造はそのまま保持し、紐づいたまま表示する。  

セキュリティに関する仕様は以下の通り：  

- 投稿データ受信  
- NGワードチェック  
- サニタイズ処理  
- DB保存  
- AIモデレーション処理  
- ステータス更新  
- UI表示制御  
- 通報・監視連携

# ■ 投稿データ処理フロー  

- 該当処理は、以下のケースで実施する：  
  1. 掲示板投稿（親文書の新規作成）  
  2. 掲示板編集（親文書・小文書の更新）  
- 登録処理はユーザーを待たせないようモデレーションなし（即時DB保存）で実施し、保存完了後にバックグラウンド（または非同期イベント）でOpenAI Moderation APIを呼び出し、ステータスを自動更新する。  

```flow
[投稿]
↓
ng_filter（NGワードフィルタ）
↓
DB保存（pending）
↓
OpenAI Moderation API (NG投稿フィルタ)
↓
状態更新（published / rejected）
↓
UIフィルタ (バッド)
↓
Report蓄積（ユーザー通報時）
↓
自動フラグ

[表示]
UI：sanitize + render
Sanitize (markdown攻撃回避)
```

# ■ ステータスおよびメタデータ仕様  

### ・ステータス（1軸：公開状態）  
- `pending`     → 未審査（投稿直後の初期状態）  
- `published`   → 審査済み（一般公開状態）  
- `rejected`    → 非公開（モデレーションにより問題ありと判定された状態）  

### ・メタデータ（別軸）  
- `risk_level`    → OpenAI モデレーションAPIから返却されたスコア/判定結果  
- `report_count`  → `square_reports` から動的に集計、またはキャッシュした通報数  
- `deleted_at`       → 削除日時（timestamp型。値が入っていれば論理削除済みとして扱う）  

---

# ■ ユーザー表示制御  

ユーザーの権限や個人設定（ユーザー情報）から表示制御情報を読み取り、DBのクエリ発行時に以下の条件でフィルタリングを行う：  

- **全投稿表示：** すべてのステータスを取得（published + pending,ただし rejected や warning はUI側でマスク処理）  
- **AIチェック済みのみ表示：** `status != 'pending'` の条件で取得  
- **安全投稿のみ表示：** `status = 'published'` かつ `deleted_at IS NULL` の条件で取得

# ■ コメント機能（小文書仕様）  

- `square` テーブル内に親文書のIDを指す `parent_id` キーを保持する。  
- 独立したコメントテーブルは作成せず、`parent_id` に値が入っているレコードをすべて「小文書（コメント）」として扱う。  
- これにより、コメントに対するコメントなど、無限階層のツリー構造を同一テーブル内で実現する。  

```square tree
文書  
 ├ 文書（コメント）  
 ├ 文書（コメント）  
 ├ 文書（コメント）  
 │   ├ 文書（コメントへの返信）  
 │   ├ 文書（コメントへの返信）  
 │   └ 文書（コメントへの返信）  
 │  
 └ 文書  
```

# ■ square_logs specs  

システム内の監視・モデレーション・通報に関わるログはすべて `square_logs` テーブルに集約する。  

### 共通カラム（Columns）  
- `id` (uuid)  
- `created_at` (timestamp)  
- `user_id` (uuid) // アクションを起こしたユーザー（通報者、またはシステム）  
- `square_id` (uuid) // 対象となった文書データのID  
- `message` (text) // ログの概要メッセージ  
- `log_type` (varchar) // ログの種類（'report' / 'moderation' など）  
- `metadata` (jsonb) // 各ログ固有の詳細データ  

### ログタイプ別のデータ構造例  

#### 1. 通報ログ（Report Log）  
- `log_type`: `'report'`  
- `message`: `'User reported this post'`  
- `metadata`:  
  ```json
  {
    "report_type": "spam",
    "reason_details": "同じ内容が何度も投稿されています。"
  }
  ```

#### 2. モデレーションログ（Moderation Log）  
- `log_type`: `'moderation'`  
- `message`: `'OpenAI Moderation API processed'`  
- `metadata`:  
  ```json
  {
    "moderation_status": "flagged",
    "categories": {
      "hate": false,
      "harassment": true,
      "self_harm": false
    },
    "category_scores": {
      "harassment": 0.87
    }
  }
  ```
